# Aspect system (TC-M4-01)

Port of the original Thaumcraft 4.2.3.5 aspect system: `thaumcraft/api/aspects/*`,
the aspect registration in `common/config/ConfigAspects.java`, and the
combination/reduction/discovery rules from `common/lib/research/ResearchManager.java`,
`ScanManager.java` and `api/ThaumcraftApiHelper.java`.

Baseline: TC-M0-04 inventory (`docs/original-content-inventory.md` §1, 48 aspects).
All values below were extracted mechanically — never hand-typed.

## Naming notes (card wording vs the original)

- The card body says "combination rules (AspectHelper)". `AspectHelper` is a
  Thaumcraft **5** class name. In Thaumcraft 4.2.3.5 (this port's baseline)
  the pair-combination and primal-reduction rules live in
  `common/lib/research/ResearchManager.java` (`getCombinationResult`,
  `reduceToPrimals`) and `api/ThaumcraftApiHelper.java` (`cullTags`). Verified
  against the decompiled source; the port keeps the TC4 locations in its
  javadoc references.
- "vis values": TC4 has **no per-aspect vis cost** on `Aspect` (that is TC5's
  `Aspect.getVis`). The TC4 vis quantity is `AspectList.visSize()` — the sum
  of the amounts in a list — ported 1:1.
- "aspect affinity/travel weights": the TC4 weighting model is the
  `cullTags` value weighting (primal ×0.9, per non-primal component ×1.1,
  per non-primal grandchild ×1.05, trim to 6). Ported 1:1 in
  `AspectCombinations.cullTags` / `cullTagOrder`.

### Reduction and culling

- `reduceToPrimals(list[, merge])` (original `ResearchManager`): every
  compound contributes both components recursively; without `merge` amounts
  add, with `merge` they combine by maximum. Example: METAL → EARTH +
  CRYSTAL → EARTH 2 + ORDER 1.
- `cullTags(list)` (original `ThaumcraftApiHelper`): while the list holds
  more than 6 aspects, compute each entry's weighted value (amount × 0.9 if
  primal; × 1.1 per non-primal component; × 1.05 per non-primal grandchild)
  and drop the lowest (first minimum in iteration order on ties).

## Essentia tables (data-driven)

`src/main/resources/data/thaumcraft/essentia/tags.json` is generated 1:1 from
the original `common/config/ConfigAspects.java` by
`scripts/extract_essentia_tags.py` (deterministic; rerunning it reproduces
the shipped file byte-for-byte modulo formatting). Format contract (enforced
by `EssentiaTagDataLoader`): `formatVersion: 1`, declared `counts` must match
the embedded arrays, every referenced aspect tag must exist in
`AspectDefinitions`.

Frozen counts (original extraction): **48** aspects, **287** item entries,
**56** ore-dict entries, **116** entity registrations. Loop expansions the
extractor performed (recorded in the file's `notes`):

- the 16 `dyes` ore-dict names,
- the 48 `Wisp` entity registrations keyed by NBT `Type` (one entry per
  aspect),
- the potion-meta loop collapsed to one wildcard entry (1.21.1 potions have
  no meta; all variants inherited the base potion tags).

Lookup semantics preserved from the original:

- `getObjectTags(ItemStack)` follows the original fallback chain: exact
  `(item, meta)` → wildcard meta 32767 → (wildcard queries only) first of
  metas 0..15. The original's `int[]`-meta registrations were expanded to
  per-meta entries by the extractor.
- `getEntityAspects(Entity)`: player special case (MAN 4; azanor/direwolf20/
  pahimar easter eggs; otherwise three aspects seeded from
  `("player_" + name).hashCode()` — same seed string as the original), else
  the entity table with the original's NBT byte/string condition matching,
  first match in registration order.

### Known seams (documented deviations, deferred by design)

- **id/meta**: entries keep original 1.7.10 ids and metas. `variantMeta()`
  currently returns 0 for modern stacks; TC's own meta-variant items map onto
  their original metas when their content milestones register them, and a
  future variant resolver maps modern variant items (wool colours, wood
  types, potion variants) onto the original `(id, meta)` pairs.
- **ore-dict names**: kept as data (`oredictTags`) for a future compat
  layer; 1.21.1 has no ore-dict, so `getObjectTags` does not consult them
  yet.
- **config-gated entries**: original registrations guarded by
  `Config.found*Ingot` flags carry a `condition` string in the data; the
  lookup ignores it until the corresponding config keys land.
- **entity NBT conditions**: 1.21.1 split some variants into separate entity
  types (wither skeleton, zombie villager). Their original conditional
  entries never match on modern entities, so those entities resolve to the
  base entry — same first-match rule as the original, different NBT reality.
- **crafting-derived tags**: `ThaumcraftCraftingManager.generateTags`
  (crafted-item bonus tags) and the wand special case belong to the
  crafting/equipment milestones.

## Discovery semantics

`ScanManager.checkAndSyncAspectKnowledge` arithmetic, ported exactly
(`AspectKnowledge.checkAndSyncAspectKnowledge`, pure part
`effectiveAmount`):

1. first discovery of a tag: send `AspectDiscoveryPayload`, add +2 to the
   gain, and capture `save` at that point (the original captures before the
   compression below);
2. if the pool ≥ `aspect_total_cap` (config, default 100): gain =
   `(int) sqrt(gain)`;
3. if gain > 1 and pool ≥ cap × 1.25: gain = 1;
4. add the gain to the pool; on success send `AspectPoolPayload(tag, gain,
   newTotal)` and return the saved amount.

`validScan`: non-empty list and, for every compound, both parents already
discovered (original `hasDiscoveredParentAspects`: primal always passes).
`applyScanKnowledge` (original `completeScan` tail): per-aspect gate,
thaumometer zeroes the amount (discovery only), registry prefix `#` adds +1,
gains collected into the returned list. The original's
`ResearchManager.completeAspect` follow-up (mark discovered + set pool +
schedule save) is carried by the attachment write itself + the attachment
sync; research-page triggers run through the TC-M3-02 research lane.

## Tests

- `AspectDefinitionsParityTest` (unit): all 48 definitions vs the frozen
  original table and vs the TC-M0-04 inventory §1; primal set; topological
  declaration order; registry-free `Aspect` behaviour.
- `AspectCombinationTableTest` (unit): exhaustive 48×48 pair table vs the
  original; reduceToPrimals (add + merge) and cullTags weighting.
- `AspectDiscoveryRulesTest` (unit): the discovery amount arithmetic.
- `EssentiaTagsDataTest` (unit): frozen counts, spot-checks against the
  original `ConfigAspects` registrations, every aspect reachable, every
  non-vanilla target resolves against `docs/content-mapping.csv`, loader
  format contract, NBT condition matching.
- `AspectSystemGameTest` (gametest): live registry (48/6/42, identity
  components, combination), in-game essentia resolution (ore-dict stone entry
  present but not consulted — documented seam, dirt wildcard meta, cow,
  player), discovery flow on the real attachment (first +2,
  repeat, validScan gate, thaumometer, registry prefix), reduce/cull on
  registry objects.
